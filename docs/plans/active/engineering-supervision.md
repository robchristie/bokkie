## Outcome and boundaries

Bokkie accepts ordinary engineering intent, retains a versioned contract,
delegates bounded Codex work, answers routine questions, reconciles uncertain
execution, assesses exact deliverables and commissions repairs. Completion
requires a qualified fixture followed by an actually supervised local knowledge
workspace, independent engineering review and separate retained acceptance.

Keep one authoritative obligation lifecycle in domain/Store. Every live
obligation has a wake-up, lease or visible attention. Worker completion leaves
acceptance pending. Persist contracts/authority, packages and relationships,
execution ownership/checkpoints, questions/resolutions, exact submissions,
acceptance and repairs. Stable command receipts and revision fencing reject
replay conflicts and stale workers/decisions. Cancellation/expiry never proves
an external writer stopped; reconcile it or isolate replacements explicitly.

Ordinary reviewed source/test/documentation landing and task-scoped processes,
the configured account, isolated databases/worktrees and a new local repository
are authorised. No global configuration changes, live Bokkie database operations,
persistent services, deployment, releases, new remote publication or private
documents. Preserve gardener restrictions and existing workflow skill owners.

  review, repository access, UI inspection and question/approval handling.
- Required: Live calibration proves fresh dispatch, question/answer, progress/result,
  follow-up, reconnect, offline completion and interruption/runtime loss.
- Required: Durable records survive restart; parent/child and dependency relations
  define failure/cancellation; authoritative state and workspace writers are fenced.
- Required: Fixture proves routine autonomous answers, incomplete-result repair,
  immediate post-dispatch restart, offline completion, lost-ack replay, stale
  replacement results, contract-bound acceptance, cancellation responsibility
  and one actionable new-authority escalation.
- Required: Plain-intent UI acknowledges durable save, supports follow-ups, request
  changes and escalation answers, and shows responsibility/next action/acceptance
  consistently with Tasks and Needs attention and existing HTTP boundaries.
- Required: After fixture qualification Bokkie dispatches and accepts the local app;
  outer intervention is recorded and affected qualification repeated.
- Required: App selects a local directory, browses/renders Markdown/internal links,
  searches a rebuildable index, handles relative attachments and missing or
  unsupported content honestly, refreshes external changes and rebuilds from source.
- Required: Pages/attachments remain unchanged, derived state lives separately,
  embedded HTML is inert and outside-directory references have explicit handling.
- Required: Long pages, code, tables, images, Unicode and broken links qualify the
  reader before broad UI implementation. Sample content is separate from source.
