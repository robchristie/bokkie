## Outcome and authority

Bokkie becomes the primary web interface for describing work, inspecting and
editing versioned tasks, arranging execution, steering work and receiving
attributable results. Definitions, progress and results remain understandable
without the originating conversation. Reduce manual transfer and repeated
tasking while retaining the obligation kernel and established delivery gates.

The 9 October 2026 assignment authorises ordinary source, tests, documentation,
refactoring and CI through independent review and standing squash-merge rules.
It does not authorise deployment, new credentials or access policies, mailbox
mutations, server updates, reboots, gateway changes or other live operations.
Prepare concrete integrations before requesting the minimum missing decision.
Continue independent authorised work while a decision is pending.

## Ownership and dependencies

Bokkie owns conversations, immutable task definitions, agreed scope and
acceptance, timing, admission, execution references, recovery, questions and
results. A host service owns start/status/events/cancel, deduplication, runtime
ownership and verified cessation. The selected workspace owns planning,
implementation, coordination, verification, independent review, CI and delivery.
Individual projects enter their project workspace; finite cross-project
campaigns enter portfolio-workspace through its registry and applicable guidance.
Portfolio owns pilot → assess → rollout; Bokkie carries progress and steering.

Dependency order: connector calibration → complete workspace task → portfolio
and bounded decisions → recurrence → retirement of replaced flows. Research
follows useful workspace execution; email observation, system observation and
isolated browser execution follow the common task/run/result contract. Memory
starts modestly alongside useful execution. Refine packages from evidence.

Exit: guidance loading, progress/questions/results, ambiguous-start recovery,
controller restart and descendant cessation are observed. If a supported seam

## Task and interaction contract

The agent populates outcome/completion criteria, scope/context, timing,
stages/progress, permitted actions/decision rules, finite execution limits and
results/history. Conversation and direct editing use the same numbered definition.
Show meaningful differences. Admitted runs pin their definition and destination;
later edits affect future work. Model tuning belongs in role profiles.
Unchanged-state waiting consumes no model calls. Routine decisions within agreed
bounds proceed; missing information, inconclusive evidence and wider scope ask.

Memory is inspectable, correctable and removable, distinguishes explicit from
inferred preferences and retains useful sources. Project knowledge stays with
its project. Memory and untrusted pages/mail/logs cannot grant permissions,
override current instructions or change runtime policy.

## Reliability and qualification

- Every non-terminal obligation retains a durable wake-up, active lease or
  visible attention condition; lifecycle transitions stay in Store/domain.
- Persist intent before external effects; never perform them in a transaction.
  Replays and lost replies cannot create duplicate jobs.
- Connection loss or lease expiry cannot establish cessation. Ownership covers
  actual writable repositories/worktrees and descendant work, and survives restart.
- Task edits cannot redirect admitted work. Agent text or successful process exit
  cannot establish acceptance. Notification failure cannot erase results or rerun work.
- Use focused deterministic lifecycle/recovery regressions, representative browser
  journeys, canonical `tools/check.sh` / affected `tools/check-ui.sh`, exact-head
  independent review, required CI, merge and post-merge CI. Reuse attributable
  evidence. Connector fixtures prove failure handling, not live capability.
- First acceptance requires one real small change delivered through its workspace
  from a conversational web request. Later portfolio demonstrations must preserve
  existing partial outcomes and never repeat completed pilots or interrupt rollouts.
- Keep package evidence and exact landed identities linked here at phase boundaries.
  The full objective remains active until every outcome is proved or a genuine
  missing access/target/authority boundary remains visible with a concrete next action.
