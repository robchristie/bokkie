# Knowledge workspace: retained operator intent

This is the product intent to submit through Bokkie's conversational runtime
after the isolated supervision fixture qualifies. It is input, not evidence
that dispatch or acceptance has occurred. Provisional application name:
**Pagefold**, with its own local repository under `/nvme/development/pagefold`.
The supervisor can resolve ordinary implementation details from this intent and
the referenced repository guidance without asking the outer delivery agent.

Build the first milestone of a local knowledge workspace using Polyorama.
I want to select a directory of Markdown pages and attachments, browse pages,
read rendered Markdown, follow ordinary relative internal links and search page
text using a generated index that can be rebuilt entirely from the directory.
Show missing links and unsupported content honestly. Support relative attachments
within the reader where practical, including local images, and explain other
attachment types. Define refresh so changes made with external filesystem tools
become visible in browsing, reading and search.

Source pages and attachments are authoritative and must remain unchanged when
opening, rendering, refreshing or indexing them. Keep generated indexes and
application state in a separate location. Treat embedded HTML as inert content;
define and enforce a policy for paths and symlinks outside the selected directory.
Use ordinary relative Markdown links and minimal metadata. No page identity
scheme is necessary unless a small explicit content contract justifies it.

Before broad UI implementation, calibrate the reader with representative long
pages, fenced code, tables, images, Unicode and broken links. Keep reusable
framework repairs in `/nvme/development/polyorama`, and application-specific
content behaviour in Pagefold. Read each repository's applicable guidance and
canonical checks. Use Polyorama's existing workspace and UI conventions, and
inspect the actual working UI through the installed Lantern workflow with
opened images and behavioural evidence. Independently review the engineering
deliverable separately from Bokkie's product acceptance.

Use only synthetic content stored separately from application source, for example
under a task-scoped fixture directory. Do not ingest private documents. Creating
the local repository and local fixtures is authorised; publishing a new remote
repository or knowledge content is not. Finish and independently review the
local deliverable without treating that publication boundary as a blocker.
Ordinary repairs to existing repositories follow their reviewed landing authority.

Editing, semantic search, ingestion, synchronisation, graph visualisation and
comprehensive authoring tools are future milestones. Do not implement them now.
Supply run/use instructions, exact source revision and verification evidence
that lets Bokkie inspect the delivered behaviour against this intent.

## Qualification ownership

The final qualifying run must use implemented Bokkie dispatch, durable questions
and decisions, submission and acceptance. The outer agent may observe and repair
Bokkie infrastructure, but cannot supply routine supervisor decisions or worker
instructions and claim the journey passed. Record interventions, their failed
acceptance condition and repeated qualification in the owning run evidence.
The fixture must force incomplete delivery and prove a repair; this application
run need not manufacture a defect if its first submission meets the intent.
