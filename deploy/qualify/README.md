# Phase 0 qualification probe

This directory qualifies `codex app-server` and the Codex Linux sandbox
inside a container on nostromo for Phase 0, against the
[sandbox invariants](../../docs/architecture.md#sandbox-invariants). It is
not a deployment. The container publishes no ports and has no Traefik route.
Its Compose projects are named `bokkie-qualify-<profile>`. Never use the
project name `bokkie`.

## Pieces

- `Dockerfile` builds the qualification image from pinned digests:
  - Codex from [`deploy/codex-release.env`](../codex-release.env), verified by SHA-256;
  - Debian 13's `bubblewrap` at an exact version;
  - users 10001 (the gateway and the single-UID users `alice` and `bob`) and 10002 (the separate-UID user `dave`), with real passwd entries and their own homes.
- `crates/bokkie-qualify` provides two binaries.
  - `bokkie-qualify` stands in for the gateway. Each subcommand prints one JSON result.
  - `bokkie-sandbox-probe` runs inside the sandbox. It makes real reads, writes, process inspections and connections, and reports their outcomes. It never prints file contents or credentials.
- `compose.yml` is the hardened base: non-root, `cap_drop: ALL`, `no-new-privileges`, read-only root, an init process, PID, memory and CPU limits, and a tmpfs `/tmp`. Two files layer the profiles under test on top of it:
  - `compose.profile-a.yml` is profile A, relaxed.
  - `compose.profile-b.yml` is profile B, targeted.
- `policy/` holds profile B:
  - its seccomp policy, generated by `make-seccomp-b.py` from Docker's default at nostromo's Engine revision;
  - its AppArmor profile;
  - the loader script.

  These derive from Moby (Apache-2.0). See `policy/LICENSE` and `policy/NOTICE`.
- `qualify.sh` is the driver. It runs on the Docker host from a clean checkout of the exact commit under test.

## Codex configuration under test

Every `CODEX_HOME` gets a `config.toml` that defines two permission profiles.

- `bokkie` allows:
  - `:minimal` read: system paths only;
  - write to the thread's workspace roots;
  - nothing else under `/data`;
  - no network.
- `bokkie-net` is the same profile with network access.

The probe also runs Codex's built-in `:workspace` profile as a control.

## Procedure

Applying profile A or B, or loading profile B's AppArmor profile, weakens
the default container confinement on nostromo. It needs the owner's explicit
go-ahead each time. The `default` profile is the control: Docker's own
confinement, which is expected to stop Bubblewrap.

```sh
deploy/qualify/qualify.sh build
deploy/qualify/qualify.sh run default --no-model
deploy/qualify/qualify.sh login a alice        # prints a device code; sign in once
deploy/qualify/qualify.sh run a
deploy/qualify/qualify.sh apparmor add         # profile B only
deploy/qualify/qualify.sh run b
deploy/qualify/qualify.sh apparmor remove
```

The sign-in lands in the `bokkie-qualify-data` volume (`/data/users/alice/codex`),
so every profile and restart reuses it. `docker volume rm bokkie-qualify-data`
removes the qualification credential when Phase 0 is done.

## What `run` checks

| Step | Evidence |
| --- | --- |
| `env` | Identity, seccomp, AppArmor label, `/proc` masks, Codex and `bwrap` versions |
| `bwrap` | Which `bwrap` binary Codex actually ran, observed from outside the sandbox |
| `sandbox-<via>-*` | Invariants 1 to 5 through `codex sandbox` (`cli`) and the app server's `command/exec` (`exec`): one user, two users with one UID, two users with separate UIDs, the built-in profile, and network allowed |
| `orphans-<via>`, `orphans-gateway` | Invariant 6: SIGKILL of `codex sandbox`, of the app server, and of the stand-in gateway leaves no sandboxed process |
| `account` | `account/read`, `model/list`, `account/rateLimits/read`, `permissionProfile/list`, `config/read` |
| `chat-start`, `chat-resume` | A persistent thread, a streamed turn, and the thread resumed after a container restart |
| `refresh`, `refresh-persisted` | A forced token refresh that survives a container restart |
| `tool-start`, `tool-resume` | "Message another Bot" through `dynamicTools`: one Bot asks another and relays its reply, then again after a container restart without passing the tool again |
| `turn-exec` | A real turn whose shell command runs the sandbox probe |

Invariant 4 treats Codex's silent procfs fallback as a failure. The sandbox
must see its own `/proc/1/cmdline`, not the container's. Every outer process
is identified by name and start time, and none of them may be visible.

Results go to `~/.local/state/bokkie-qualify/<run>/<profile>/` on the host.
They stay out of the repository. The Phase 0 report in `docs/` records the
conclusions.
