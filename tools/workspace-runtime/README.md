# Workspace execution host

This development-host worker connects outward to Bokkie and runs an immutable
assignment through its registered workspace. Bokkie owns the task definition,
admission, lifecycle, questions and acceptance. The workspace owns planning,
source changes, independent review, checks, CI and ordinary delivery. This route
has no engineering supervisor and does not use desktop chat tools as an external
API. It installs no service or deployment.

The [calibration record](../../docs/workspace-execution/calibration.md) separates
the actual workspace/tool/descendant observations from deterministic recovery
tests. This adapter accepts the qualified Codex CLI `0.160.1` only.

## Private configuration

Prepare canonical existing directories for runtime state, task scratch, permitted
repositories/worktree roots and shared Git storage. Keep runtime state, this
configuration and the host token outside every writable resource. Runtime
directories and the token file must belong to the current account and exclude
group/other permissions. Use one project/profile revision for the exact host-local
allowlist; changing it cannot redirect previously admitted jobs.

The host token is a distinct existing 64-character hexadecimal credential sent
as `X-Bokkie-Host-Token` for the Bokkie host exchange route. The browser mutation token provides no host
authentication. Bokkie must enrol the host and configured token digest explicitly;
this script does not obtain account credentials, enrol a production host or change
access policy. Redirects are rejected so the authentication header cannot be
forwarded to another origin. Plain HTTP is accepted only for a loopback origin.

An existing edge which requires HTTP Basic authentication keeps that policy.
Optionally select `edge_authorization_file` in this private configuration: an
existing canonical regular file owned by the current account with mode `600`,
containing one `Basic …` Authorization value. The worker reads it only on the
development host, uses it for the edge's `Authorization` header and separately
sends the Bokkie host token. Its credential bytes are never logged, copied into
task state or generated by this adapter; its path is masked inside each task
boundary and excluded from writable resources. Omit the field for direct local
qualification. Selecting an existing edge credential requires the operator's
authorised target/access choice; this source setup neither accesses deployed
Bokkie nor weakens its edge authentication.

Create a private JSON configuration using this shape, replacing every path and
identity with its actual fixed value:

```json
{
  "version": 1,
  "host_id": "development-host",
  "server_url": "https://bokkie.example.org",
  "runtime_root": "/absolute/private/workspace-runtime",
  "token_file": "/absolute/private/host-token",
  "codex": "/absolute/canonical/codex",
  "bwrap": "/absolute/canonical/bwrap",
  "poll_seconds": 2,
  "projects": [{
    "id": "registered-project-id",
    "revision": 1,
    "host": "registered-host-reference",
    "workspace": "/absolute/project-workspace",
    "profile_revision": "workspace-v1",
    "permitted_actions": ["ordinary_code_delivery"],
    "limits": {"max_seconds": 7200, "max_turns": 4, "max_tokens": 1000000},
    "write_roots": ["/absolute/product", "/absolute/task-worktree-root", "/absolute/task-scratch"],
    "git_common_dirs": ["/absolute/product/.git"],
    "scratch": "/absolute/task-scratch",
    "role": {},

    "readonly_mcp_servers": [],
    "reviewer": {

      "config_file": "/absolute/private/exact_head_reviewer.toml"
    },

      "repositories": [{
        "repository": "owner/product",
        "checkout": "/absolute/product",

        "required_checks": ["Actual required check name"]
      }]
    }

```

`role` contains only `model` and `model_reasoning_effort`; omission snapshots the
account's current exact pair and configuration digest into the admitted profile.
Set the pair explicitly when the selected role must remain independent of future
account choices. Named role tuning remains in host-local role files.

For an observed independent Codex review, derive the existing named reviewer
profile into a task-local file, preserving its model, effort and instructions,
with `sandbox_mode = "read-only"` and `approval_policy = "never"`. The worker
passes that file through the named `exact_head_reviewer` configuration and pins
its digest. Do not modify global account configuration. A completed child must
have runtime-reported parent linkage and that role, a completed final-answer
turn, and the exact `Verdict: PASS` / `Reviewed head: <full revision>` report.
An implementation child or the root's own PR comment cannot satisfy review.
An independent GitHub `APPROVED` review at the exact head is also supported.

For Bokkie, the current authored CI names are `Plan governance`,
`Locked backend checks`, `Locked attention UI checks` and
`Authenticated manifest and worker`. Select canonical local commands from the
affected product's guidance; a documentation-only Bokkie task uses
`tools/check.sh`, with `tools/check-ui.sh` required when its UI/shared contract
scope is affected. The host observes each exact shell command on a clean candidate
at start/completion and checks required CI separately on candidate and merge.

## Operate and inspect

```sh
python3 tools/workspace-runtime/worker.py --config /absolute/private/host.json allowlist
python3 tools/workspace-runtime/worker.py --config /absolute/private/host.json preflight registered-project-id
python3 tools/workspace-runtime/worker.py --config /absolute/private/host.json run
python3 tools/workspace-runtime/worker.py --config /absolute/private/host.json status
python3 tools/workspace-runtime/worker.py --config /absolute/private/host.json cancel execution-id
python3 tools/workspace-runtime/worker.py --config /absolute/private/host.json verify execution-id
```

`preflight` creates a separate retained diagnostic execution, starts no model,
checks the actual local environment, instruction route, role and permissions,
then proves cessation. Preflight jobs are never sent to Bokkie. `run --once`
performs one exchange for a bounded transport check. Stop/restart `run` with the
same configuration to reconnect detached brokers and replay their retained events.
Stopping the worker does not cancel the assignment. Cancellation is monotonic
and remains unconfirmed until the cleanup owner proves cessation.

`verify` acquires missing read-only delivery evidence for an already ceased job
and emits another observation of the identical result and cessation. It never
starts another model turn. It is useful when completed delivery was retained with
acceptance pending because review or CI evidence was temporarily unavailable.
The Bokkie Store decides whether this later verification permits acceptance.

## Ownership, containment and recovery

The account-wide registry at
`~/.local/state/bokkie/workspace-resource-locks` atomically reserves all canonical
writable resources. Equality and ancestor/descendant overlap block another job,
including a shared Git common directory across otherwise separate worktrees.
Markers and lock inodes are retained. A dead broker, timeout, transport loss or
expired lease cannot release a reservation. Only an exact trusted `not_started`
or `descendants_reaped` receipt does so. Do not delete state or markers to force
replacement of an uncertain owner.

One detached broker holds an exclusive execution lock. It commits its launch
marker before spawning any cleanup owner/payload. A repeated dispatch hashes
and compares the entire immutable payload; a changed payload conflicts. A later
broker seeing that marker never launches a replacement. A lost app-server start
reply stops/reaps the boundary; it does not retry `turn/start` or use thread resume
as proof of in-flight recovery.

The payload runs in a private PID namespace with a read-only host root and only
declared writable resource mounts. Private per-execution Codex state preserves
existing account config/auth, personal guidance, installed skills and role files
as read-only mounts. Host outbox, answers, reservations, configuration and token
are hidden/protected inside the boundary. The running host adapter's own source
directory is mounted read-only even when its product repository is writable;
source work uses the selected task worktree. Read-only credential refresh failures
remain actionable account-maintenance failures outside this adapter. Dependency
caches or preview scratch needing writes must be declared resources; ambient
`/tmp` grants are excluded. A separate trusted subreaper observes the broker
through a pidfd and adopts/kills/reaps every remaining descendant generation,
including `setsid` descendants and the Bubblewrap constructor window. Its own
uncatchable death leaves ownership uncertain rather than presumed stopped.

The controller pins an absolute `admitted_at`/`deadline_at`; arrival, retries and
restart never extend it. Runtime dispatch is bounded by that wall deadline,
finite turn/context observations and configured app-server thread capacity. Token
accounting includes cached input and is an observed cancellation threshold; one
turn can contain multiple inference/tool steps and overshoot before its receipt.
The host starts only one root turn and never silently relaunches it.

The event outbox retains at most 4,096 events / 16 MiB per execution, reserving
terminal capacity; private runtime observations retain at most 64 MiB. Exchanges
contain at most 64 unacknowledged events and 1 MiB, with each event capped at
256 KiB. Exact sequenced replay is safe;
gaps or changed receipts fail closed. Answers are immutable by question identity
and retained before delivery. There are at most 128 retained jobs per configured
runtime root; capacity exhaustion remains an explicit operational condition.

Structured results remain untrusted. Verification requires every criterion,
allowlisted merged PR/candidate/tree identities, independent exact-head review,
attributable canonical command observations and successful required checks on
both candidate and merge revisions. Verification uses bounded read-only GitHub
queries, never model completion prose, and retains a failed verification alongside
the submitted result. Notification failure cannot erase this state or rerun work.

## Focused checks

```sh
python3 -m unittest discover -s tools/workspace-runtime -p 'test_*.py' -v
python3 -m unittest discover -s tools/tests -p 'test_workspace_runtime.py' -v
```

The canonical governance wrapper includes this zero-model suite. Fake peers
prove recovery/trust handling; the actual reaper test proves local descendant
cleanup. These checks do not establish a real web-created task, live source
delivery, runtime child-review attribution or a deployment.
